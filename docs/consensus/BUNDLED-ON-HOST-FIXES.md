# Fixes after review: the bundled stack built on the host, 2026-09-09

Branch `feat/bundled-on-host` at 349c841 (22 commits over 44d1fb5). Two reviews ran in parallel on a detached copy: a security review (section S) and a correctness review (section C). Each item is one test-first commit unless it says otherwise. The rules of the brief `BUNDLED-ON-HOST-BRIEF.md` still apply.

## S. Security review findings

S1 (HIGH). `PostgresStackVersionRepository.removeGuarded` (manager/src/domain/versions/PostgresStackVersionRepository.ts:339-340) still runs `SELECT 1 FROM bundled_shipments WHERE version_id = $1`, a table migration 030 drops on every database. The first `DELETE /versions/:id` after the upgrade fails with "relation bundled_shipments does not exist" and version removal is dead on the host. It escaped because `manager/test/database/versionRemoval.test.ts` runs only with `T04A_TEST_PG_PORT` and itself still inserts into the dropped table (:438) and iterates it (:259). Fix: remove the query and the now unreachable `'shipments'` member of `VersionRemovalHold` (manager/src/domain/errors/StackVersionRemovalHeldError.ts:1), drop the three `bundled_shipments` blocks from `versionRemoval.test.ts`, and run that file against the disposable Postgres (`T04A_TEST_PG_PORT`, database `t04a_test`) to prove it. Then grep the whole repository once more for `bundled_shipments`, `shipment`, `sealed`, `materialization`, `claims` in src, scripts, deploy, frontend and test, and remove every leftover in this commit. Evidence from Fable's own run of the whole database directory on the slice, with one database per task (`t01_test`, `t04a_test`, `t04b_test`, `t06_test`, `t08_test`, `t09_test`, `t10_test`, `t11_test`, `t12_test`, every `*_TEST_PG_PORT` set to 55432): 497 tests, 464 pass, 11 fail, 22 cancelled, the failures being `versionRemoval.test.ts` and `buildSnapshotClaim.test.ts` ("claim refuses a version row removed after its read" and its `describe` twin), all with `relation "bundled_shipments" does not exist`. Both files pass on the base 44d1fb5. The definition of done for this round includes that whole directory green, run exactly that way, and the count reported.

S2 (HIGH). `replaceAtomically` (manager/src/domain/versions/hostConfigCapture.ts:190-199) writes the temp file with no mode, so the carry-over (legacyHostConfig.ts:31-32) and the completion (hostConfigCompletion.ts:98-100) leave `.env`, `deploy/config.json` and every engine env at 0644, root-owned, under a 0755 versions root. Those files hold SRT_PASSPHRASE, API_AUTH_TOKEN, SRS_WEBHOOK_TOKEN and the bee passphrase. Verified by running both functions against a 0600 input: the outputs measured 0644, and an existing 0600 `.env` measured 0644 after completion. Fix: write the temp file with mode 0o600, then before the rename chmod it to the mode the target file has when one exists, 0o600 otherwise, so an operator's `chmod 600` survives a build and a carried-over file keeps the mode it had in the legacy tree. The revision manifest gets the same treatment. Test: a 0600 input stays 0600 after carry-over and after completion, a 0640 input stays 0640, a new file is 0600. Set `process.umask(0o022)` in the test so the result does not depend on the machine.

S3 (MEDIUM). manager/scripts/stack-version-build.sh: the existing-clone path (:101-110) fetches from whatever `remote.origin.url` the clone holds, so the https-only check on `$REPO_URL` (:80-83) applies only to the first build. Anyone who can write into the versions root (bind-mounted read-write into the api container) can repoint `origin`, or set `core.fsmonitor` or `core.sshCommand` in that `.git/config` and get command execution from the fetch, as root in a container that holds the Docker socket. Fix: `git -C "$REPO" remote set-url origin "$REPO_URL"` right after the clone exists and before any fetch, on both the branch and the commit path. Test in `stackVersionBuildScript.test.ts` (script text, and the live local-repository test: repoint origin to a bogus url in the fixture clone, run the script, assert it fetched from the fixture url again).

S4 (MEDIUM). The carry-over follows symlinks: `hostConfigFilesOf` (hostConfigCapture.ts:77-88) uses `existsSync` and `readFile`, both of which resolve links. A `.env` symlink planted in the legacy tree (the one tree a deploy never overwrites, mounted into engine containers) is read in the api container's namespace, where the host root is mounted at `/host/rootfs`, and its target becomes generation 1 of the bundled settings, copied into every build and shown by the future settings page. Fix: in `hostConfigFilesOf`, a path counts only when `lstatSync(p, { throwIfNoEntry: false })?.isFile()` is true, so a link is not a host input file, and a log line names a link that was skipped. Test: a symlinked `.env` in the legacy tree is not carried over and is named in the log, a regular file is.

S5 (LOW). deploy/deploy.sh:49 and :192: `BUNDLED_TIMEOUT` comes from the invoking environment and lands inside single quotes in the remote heredoc, so a value with a quote closes the quoting. Fix: after :49, refuse anything but whole seconds (`^[0-9]+$`) with a clear message. Test in `managerDeployScript.test.ts` (script text).

S6 (LOW). deploy/deploy.sh:44 and :123: `SSH_TARGET="${1:-viewer}"` reaches `ssh "$SSH_TARGET"`, and a leading dash makes it an option. Fix: refuse a target that starts with a dash. Test in `managerDeployScript.test.ts`.

S7 (LOW). manager/test/unit/stackVersionBuildScript.test.ts:170: the live test spreads `process.env` and sets `HOME` and `XDG_CONFIG_HOME`, but a developer's `GIT_CONFIG_GLOBAL` or `GIT_CONFIG_SYSTEM` outranks `HOME`, so the `insteadOf` rewrite would not apply and the fetch would go to github.com (and fail, since the fixture commit is not there). Fix: set `GIT_CONFIG_GLOBAL` to the private home's `.gitconfig` and `GIT_CONFIG_NOSYSTEM=1` in that environment.

Checked and found sound by the security review: argv-only command construction with re-validation in the script, the pin accepting only 40 lowercase hex, the trigger surface behind the session gate with no ref from the body, key names only in logs, no other leftover of the removed path, nothing copying host inputs outside the version root.

## C. Correctness review findings

C1 (CRITICAL). The same leftover as S1, seen from the other side: `removeGuarded` (PostgresStackVersionRepository.ts:339) queries the dropped table, `versionRemoval.test.ts` still inserts into it (:434-450) and lists it (:259). One fix, S1, closes both.

C2 (HIGH, process). The database suite skips a file silently when its `*_TEST_PG_PORT` is unset, and a skip counts as nothing in the summary. Nine variables gate the 31 files (T04B 8, T01 8, T11 4, T09 3, T12 2, T10 2, T04A 2, T08 1, T06 1). Every run you report must set all nine and create the nine databases named in S1. Report the counts from that run.

C3 (HIGH). `ManagerUpgrade.ts:88-92`: `guard.release()` comes after `await operations.awaitBundledBuild(request)`, and the catch releases only when `effectStarted` is false. `awaitBundledBuild` polls Postgres for up to twenty minutes (ComposeUpgradeOperations.ts:199-212) and does not catch its own read errors, so one failed query after the api is verified leaves `<versions>/.manager-upgrade` behind and the next deploy refuses with `UPGRADE_ALREADY_OWNED` until a person removes it. Verified with a probe against the real `runManagerUpgrade` with `awaitBundledBuild` throwing: the guard root was still there. Fix: the bundled wait runs after the guard is released, or in its own try that releases before rethrowing. The design says the wait must never hold the guard, because the manager is already running. Test: `awaitBundledBuild` throws, the guard root is gone, the error is reported.

C4 (MEDIUM). `hostConfigCompletion.ts:94` reads each live file outside the lock and `commitHostConfig` (:100) takes `.config.lock` only for the write, so an operator running `stack-config-edit.sh` between the read and the commit loses the edit: completion writes back the bytes it read plus the appended keys, and `commitHostConfig` has no expected-generation check. `legacyHostConfig.ts:26` has the same shape (the emptiness check outside the lock). Fix: hold the config lock around the read and the commit in both (one acquisition, `holdHostConfigLock`), or give `commitHostConfig` an `expectedGeneration` that refuses on a mismatch and use it. Test: with the lock held by a simulated editor, completion waits (bounded) and then sees the editor's bytes, or with a generation bump between read and commit the commit refuses and the completion retries once.

C5 (MEDIUM). "Existing lines byte for byte untouched" is not tested: a mutation that strips every comment line from the operator's file before appending passed all 27 tests in `hostConfigCompletion.test.ts` and `bundledPublication.test.ts`, and so did a `trimStart()` mutation, because no fixture live file has a comment or a blank line. Fix: a case whose committed `.env` carries a comment, a blank line, a line with trailing spaces and a CRLF line, asserting the exact bytes after completion (prefix unchanged, then the sample lines). Prove it with the mutation before you commit the test.

C6 (MEDIUM). Same as S7: `stackVersionBuildScript.test.ts:170` builds the child env from `process.env`, so an ambient `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM` or `GIT_CONFIG_COUNT` defeats the `insteadOf` rewrite and puts the test on the network. Fix: `GIT_CONFIG_NOSYSTEM: '1'`, `GIT_CONFIG_GLOBAL: join(home, '.gitconfig')`, `GIT_CONFIG_COUNT: '0'` in that environment.

C7 (LOW). `ComposeUpgradeOperations.ts:122-125` (`outcomeOf`): the row counts as failed on `lastError !== null` with `gitRef === commit`, which reports the previous boot's error when `ensureBundledBuild` throws before `markBuilding` and `index.ts:220-222` swallows it. And it calls the row ready without `deployRootProblem`, while boot's `deploysBuildOf` (StackVersionService.ts:777-780) requires it, so the upgrade can print ready for a build the next boot rebuilds. Fix: one shared predicate for "deploys from a complete build of this commit" used by both (export `deploysBuildOf` or move it next to the record type), and the wait treats a `lastError` as this upgrade's only when `builtAt` or the row's update time postdates the wait's start. Say what you chose.

C8 (LOW). `managerUpgrade.ts:161` makes `--bundled-timeout` required while `ComposeUpgradeOperations.ts:53` carries the 1200 default the brief asks for: make the flag optional with that default. And on a bundled failure the CLI prints the receipt JSON then throws (:173-175), while `deploy/deploy.sh:185` captures stdout in `RECEIPT="$(...)"` under `set -e`, so the receipt is discarded and only stderr survives. Fix: in the deploy, assign the output before checking the exit status (`set +e` around the capture, or `if ! RECEIPT=$(...)`), print the receipt, then exit non-zero.

C9 (LOW). Leftovers: `index.ts:201` "before the publication of a shipment prunes", `StackVersionService.ts:164-165` "belongs to the guarded shipment flow", `StackVersionRemovalHeldError.ts:1,6` the `'shipments'` hold kind (S1 covers it), a doubled blank line at `PostgresBuildLedger.ts:217-219` and `hostConfigCapture.ts:8-9`. One `chore:` commit.

C10 (LOW). The bundled card's enabled Update state is asserted nowhere: `versionText.test.ts` covers the hint only. Add a render test of `VersionCard` for the bundled row (button enabled, the new wording, the commit shown) with whatever the frontend test setup already offers for components. If no component render setup exists, say so and cover the enabling condition as a pure function instead.

## R. Third round, from the targeted re-review of the fixes (2026-09-10)

All fourteen items above were confirmed closed, with mutations that turned the new tests red. What remains, one test-first commit each, in this order:

R3. The wait then sees a moved row within one poll. Tests: each of those paths moves the row with a reason naming the cause, the "already on the pin" path leaves the row untouched, and the wait reports failed within two polls instead of timing out.

R6. `docs/features/stack-versions.md:25` still lists "shipment records" among the removal holds. Remove the words.
