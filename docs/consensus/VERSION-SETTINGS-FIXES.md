# Fixes for the version settings slice, from the reviews of 637d758 (2026-09-10)

For the implementing agent, on branch `feat/version-settings`. Same rules as the brief: tests first, one fix per commit (a `test:` commit then a `fix:` commit, or one commit when they are one logical unit), no em-dashes or semicolons in prose, never the host, never push, never a `.env` of the submodule except the samples, never a value in a log or a test's failure output. ## F. Fable's findings

F1 (HIGH, design gap against D12). `CONFIG_SEEDS` (StackVersionService.ts:119) seeds only `.env` and `deploy/config.json`, so a version added in the UI never gets `engines/<engine>/.env` in its config root. Its settings page shows no engine section, and `SRT_PASSPHRASE`, `SRS_WEBHOOK_TOKEN`, `OME_ADMISSION_SECRET` and the ABR knobs cannot be set at version level, so the engine half of `versionSuppliedSecrets` never applies. Only the bundled version gets engine envs, by carry-over, and only where the host had them. The stack's `deploy/scripts/_lib.sh` `ensure_engine_env` copies `engines/<engine>/.env` when it exists and the `.env.sample` otherwise, so seeding the live file from the sample changes nothing a deploy reads. Fix: seed `engines/<engine>/.env` from `engines/<engine>/.env.sample` for every engine the build tree ships, in `seedHostConfig`, under the same lock, never over a file that exists, walking the same pairs `hostConfigCompletion.ts` walks (share `samplePairsIn`). Test: the first build of a v3 fixture version seeds `engines/srs/.env` and `engines/ome/.env`, the GET shows both engine sections with the samples' descriptions, a carried-over engine env is not overwritten, and a value saved for `SRS_WEBHOOK_TOKEN` in the engine section is what the next deployment gets (stackSecrets.test.ts already reads the engine env of the build).

F4 (LOW, page). The masked inputs need `autoComplete="off"` in `SettingsEntryField.tsx` so a browser password manager does not offer to save or fill them.

## C. Correctness review findings (all verified by the reviewer with probes and mutations)

C1 = H1 (HIGH). A refused apply leaves the page at the generation its own save moved past: `saveAndApply` (VersionSettingsPage.tsx:112-120) never reaches `load()` when the apply throws, so the next Save is refused as `settings_changed` about the operator's own save. Fix: reload after a successful save whatever the apply did (`try { apply } finally { await load() }`), and carry the PUT's answered generation into the page state. Browser test: apply refused with `stack_build_busy`, then Save again is not refused and the footer shows nothing changed.

C2 = H2 (HIGH). Apply with nothing changed publishes another identical build (-r1, -r2, -r3 measured), each clears the version's approval (`stackPublicationSql.ts:10`) and walks the protected-build window. Fix: `publishSettingsBuild` calls `completeBuildOf(name, commit, generation)` first and answers that build id without making a directory, with `reused: true` in `StackSettingsApplied`. The page disables Save and apply when there are no edits and the current build already carries the current generation (needs C5), and says "Build X already carries these settings" on `reused`. Test: apply twice, one directory, same id, `reused` true the second time, `tested` untouched by the second.

C3 = H3 (HIGH, test). `versionSettingsSave.test.ts` does not pin the property it is named for: moving the revision read outside the lock left it green. Fix: a deterministic interleave. The test takes `.config.lock` itself, sends a PUT that then waits on the lock, writes a newer revision by hand while holding it (files plus `.config-revision.json` at generation 2, what an ssh commit does), releases the lock, and asserts the PUT answers 409 `settings_changed` with generation 2. Prove it red against the mutation (revision read before the lock) and say so in the commit message.

C4 = H4 (HIGH). A value the stack's loader reads differently is written through: `abc #notacomment` becomes `abc`, `  padded  ` loses its padding, `"quoted"` loses its quotes (`_lib.sh:601-641`), and the manager's own `parseEnvText` reads a third way, so `versionSuppliedSecrets` can say the version supplies `API_AUTH_TOKEN` while the container starts with a truncated one. Fix: one rule in `common`, `envValueProblem(value)`, refusing a value with leading or trailing whitespace, an unquoted whitespace-then-`#`, or a leading quote without its matching closing quote, with a message that says why and how to write it. The PUT schema uses it (400 naming the key, never the value) and the page shows the same problem under the field before saving. Test both sides.

C5 = H5 (HIGH). Nothing tells the operator a saved change has not reached any build. Fix: `StackSettings.buildGeneration: number | null`, the current build manifest's `inputGeneration`, read in `settingsOf`. The page says, when it differs from `generation`: "Saved as revision N. The current build carries revision M, so new deployments do not have these changes yet. Apply makes a build that does." and shows "applied" in the header when equal. Browser test for both states.

C6 = M1 (MEDIUM). A settings file that is a symlink or missing drops out of the GET silently, and a PUT naming a linked path says the file is absent. Fix: `StackSettings.leftAlone: string[]` from `hostConfigNonFilesOf`, the page shows a warning naming each path ("there is a link at .env and nothing here reads it"), and the PUT refusal says link or directory rather than absent. Test both.

C7 = M2 (MEDIUM). Apply hard links the previous build's per-deployment env files (`.env.<profile>`, `engines/<engine>/.env.<profile>`), so `writeProfileEnv`, which truncates in place, then writes into the published build the new one was made from (measured: same inode, old bytes changed). It also carries the old per-profile engine env into the new build, so a redeploy after an engine setting was applied would keep the old value, because the stack's `ensure_engine_env` only creates that file when it is missing. Fix: the clone skips every file whose name starts with `.env.` except `.env.sample`, at the root and under `engines/*`. Test: the old build directory's content hash is unchanged across an apply and a deploy on the new build, and the new build holds no `.env.<profile>`.

C8 = M3 (MEDIUM, test). Nothing guards the release of the build mutex on apply's throwing path. Test: apply a not-ready version (409), then `POST /versions` still starts a build.

C9 = M4 (MEDIUM). The description run absorbs a commented-out assignment of another key, so `ORPHAN_REAP_MS` gets `HLS_FRAGMENT`'s documentation in the real sample, and rule lines (`--- Logging ---`, `=== ABR ladder ===`) open descriptions. Fix: the run ends at a comment line that is itself an assignment of a different key (the lines above it document that key), a commented-out assignment of the same key stays in the run (the `BEE_PUBLISHERS` example), and a comment line that is only a rule (`#` then three or more `=` or `-` with optional words) is dropped. Test against the real `.env.sample` and `engines/srs/.env.sample` of the v3 fixture: `ORPHAN_REAP_MS` gets its own two sentences, `BEE_PUBLISHERS` keeps its block including the example line, `LOG_LEVEL` and `ABR_ENABLED` do not open with a rule.

C10 = M5 (MEDIUM). `settings_not_ready` says "this one has none" for three conditions, and apply on a legacy row says "Build null cannot be read". Fix: three reasons, never built, a root without a committed revision (commit one with the editing script or Update the version), and a legacy row (see C12), and no null in any message.

C11 = M6 (MEDIUM). `remove` in the PUT cannot be triggered from the page. Fix: a Remove action on an entry the sample does not declare (`sampleValue === null`), sending `remove: true`, with the draft treating a removed key as an edit and Discard bringing it back. Test the draft and the page.

C12 = M7 (MEDIUM). The Settings button is enabled for a legacy row, so GET and PUT can work against a flat root and apply fails with a null in the message. Fix: the button is enabled only for `layout === 'builds'` with a `buildId` (a legacy row says settings appear after Update has built it here), and `applySettings` refuses a non-builds row with `settings_not_ready` and that reason.

C13 = M8 (MEDIUM). Covered by the modes work in section S.

Left as noted, not fixed: L1 (a save that appends to a file with no trailing newline adds one), L2 (an appended line ends with `\n` even in a `\r\n` file), L3 (a repeated key gets every line rewritten), L4 (the session gate is pinned by mount order in serverGateOrder.test.ts, no per-route case), L5 (the pre-existing acquireDockerBeeStream flake under load).

## S. Security review findings (all verified by the reviewer with requests against the test app and mutations)

S1 = H1 (HIGH). Every build's copy of the settings files is world readable: `publishStaging` writes them with no mode (StackVersionService.ts, the inputs loop) so the umask decides, measured 644 in a 755 build directory, and `writeSettingsInto` in the apply path writes 0600 and then chmods to the source build's mode, carrying the 644 into every applied build. The per-deployment `.env.<profile>` that `writeProfileEnv` writes (envUtils.ts:416, `writeFileSync` with no mode) holds the generated secrets at the same width. The manager's container runs as root (no `USER` in manager/Dockerfile, no `user:` in manager/docker-compose.yml), so on the host these are root-owned files readable by every account. Fix: `{ mode: 0o600 }` on all three writes, `writeSettingsInto` keeps 0600 and no longer takes the source mode, and `writeProfileEnv` chmods an existing file to 0600 after writing it. Test each by stat, and the apply test covers the file the old build lacked (M8 of the correctness review).

S2 = H2 (HIGH). `SRS_CONF_FILE` and `OME_CONF_FILE` become a Docker bind-mount source (`${SRS_CONF_FILE}:/usr/local/srs/conf/srs.conf.custom:ro` in the version's compose override), and `writeProfileEnv` checks its own per-deployment value against `ENGINE_CONFIG_FILE_RE` for that reason, but the settings PUT writes the same keys into the version's base env with only the generic checks, and for a deployment without a config file of its own the version's line stands. Fix: the shared value rule of C4 takes the key too, `settingValueProblem(key, value)`, and for these two keys accepts only empty or an absolute path of `[A-Za-z0-9._/-]`. The regex moves to `common` so both sides use one. Test: a PUT with `SRS_CONF_FILE=$(whoami)` is refused with 400 naming the key.

S3 = M2 (MEDIUM). The GET answers every secret with no `Cache-Control: no-store` (headers measured: an ETag and nothing about caching). Fix: `res.setHeader('Cache-Control', 'no-store')` in the GET handler, as routes/engineConfig.ts:28 does. Test the header.

S4 = M3 (MEDIUM). A held config lock (what the ssh editing script holds) turns into HTTP 500 `internal_error` with a logged stack after the ten second wait, on GET, PUT and apply alike, and the message that names the root and the `--unlock` recovery never reaches the operator. Fix: a typed `HostConfigLockHeldError` thrown by `holdHostConfigLock`, mapped to 409 `settings_locked` with its message, and the page shows it as a refusal with a retry action. Keep the test short by letting the wait be set through the service (a constructor option), or accept one ten second test and say so.

S5 = M4 (MEDIUM, test). Removing the `isFile` filter in `hostConfigFilesOf` left every test green, and with it removed a symlink at `engines/ome/.env` or at `.env` pointing outside the root was accepted by the PUT. Add the two cases to versionSettingsRoutes.test.ts: 400, the link's target unchanged byte for byte, the path absent from the GET's files and present in `leftAlone` (C6).

S6 = M5 (MEDIUM, test). The only new log line prints key names, and changing it to print `key=value` left every test green. One assertion over `describeSettingsSave` that a value passed in does not appear in its output.

S7 = M6 (MEDIUM). No bound on what one PUT carries: 4000 entries in one file and 200 repetitions of one file were accepted, and a body over the 256 kB limit answers 500 because body-parser's `PayloadTooLargeError` has no branch in the error handler. Fix: `.max(16)` on `files` and `.max(512)` on `entries`, a `PayloadTooLargeError` branch answering 413 `payload_too_large`, and a repeated path in one PUT refused with 400 (L6: `editedBytes` re-reads the file per edit, so the first of two edits of one path is lost). Tests for all three.

S8 = L1 and L2 (LOW). The one-line guard rejects only `\r` and `\n`, so a NUL, a vertical tab and U+2028 were written literally: the C4 rule also refuses the C0 control range and U+2028 and U+2029. A yup type error echoes the submitted value in the 400 body: `.typeError('a settings value is text')` on `value`, `text` and `key`.

S9 = L3 and L4 (LOW, tests). The path allowlist regex in the schema and the 64-hex stack secret guard in `writeProfileEnv` are both real and both untested (mutations m2 and m13 stayed green). One schema test that a traversal path is refused by the schema alone, and one `writeProfileEnv` test that a stack secret that is not 64 hex is refused.

S10 (from the review's point 8). `versionSuppliedSecrets` treats a value in either file as supplied, but the root env wins in the stack's deploy script, so a key the base sample declares blank (`API_AUTH_TOKEN`) and the operator sets only in the engine env leaves an empty root line winning while the manager generates nothing. Fix: a key counts as supplied by the base env when the base env assigns it non-empty, and by the engine env only when the base env does not assign it at all. Tests for both.

Left as noted, not fixed: L7 (no console call exists in frontend/src, verified by reading), L8 (`X-Powered-By` served and no security headers, pre-existing, for T21), and the first-run unit flake the reviewer saw once and could not reproduce (the two load-sensitive tests, known).

## D. A decision for Levi, not for this round

D14 (from the security review's point 9). Any signed-in user can read and set these values, which matches every other route today: only user management asks for the admin flag, and profiles, deploys, targets and versions have no role check. The base env also decides `BEE_UPLOADER_API_BIND`, the interface the Bee node's unauthenticated API listens on, so this page hands every signed-in account the ability to change that binding for every future deployment. Recommendation: leave it consistent now, and decide later whether version settings and version management become admin-only. Levi decides.
