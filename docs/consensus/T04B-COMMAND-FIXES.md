## A. Two defects that break the first real deploy

**A1. The first-use probe counts the upgrade's own container.** `manager/src/cli/ComposeUpgradeOperations.ts:209` asks `docker compose ps -aq api`, and `-a` includes the one-off container the deploy started with `docker compose run`, so on a clean host the probe sees itself and refuses with "This host has an api container but no manager_manager-pg volume". Replace every "does a container of this service exist" question with a plain docker probe filtered by labels and excluding one-offs: `docker ps -aq --filter label=com.docker.compose.project=<project> --filter label=com.docker.compose.service=<service> --filter label=com.docker.compose.oneoff=False`. Keep `docker compose ps -q <service>` (no `-a`) for "is it running", which never lists one-offs. Test with a fake answer that returns the one-off shape and prove first use is still detected.

**A2. Compose may create the project's volumes when it prepares the one-off container, which would hide first use from the probe inside it.** So the deploy script decides first use on the host before `docker compose run`, where nothing has been created yet, and hands the answer in. In `deploy/deploy.sh`, in the remote block before the run: read the volume with `docker volume ls -q --filter name=^manager_manager-pg$`, the api and postgres service containers with the label probe above. No volume and no api container and no postgres container means first use: pass `--first-use` to `manager:upgrade`. No volume but an api container means the database was removed under an installed manager: print that sentence and exit 1 before the run. Inside `manager:upgrade`, `--first-use` is a switch. `readPublication` requires the schema to read `fresh` when the switch is set, or when its own probes find no volume, no api and no postgres container, and refuses otherwise with the sentence that is there today. `managerDeployScript.test.ts` asserts the three probes and the abort exist before the run line.

**A3. `docker compose run` drains the remote script.** The remote block is fed to `bash -s` over ssh, and `docker compose run` keeps stdin open by default (`-i` is on, `-T` only drops the TTY), so it swallows the rest of the script: the receipt echo and the PUBLIC_HOST check never run, or a truncated line runs. Append `< /dev/null` to the `docker compose run` line and to the `docker compose exec -T api` line in `deploy/deploy.sh`. Test in `managerDeployScript.test.ts`: both lines carry `< /dev/null`.

**A4. The deploy script never proves `${PUBLIC_EDGE_FLAG}` reaches the command.** Add to `managerDeployScript.test.ts` an assertion that the run line ends with `--toolchain '${TOOLCHAIN}' ${PUBLIC_EDGE_FLAG}` followed by the stdin redirection. Same commit as A3's test.

**A5. Only the first listed Postgres container decides health.** `ComposeUpgradeOperations.ts:203-206` and `:224-225` take the first entry of `docker compose ps -a --format json postgres`. Use "some container is running and healthy" for the healthy check and "no container at all" for absence. Test with two entries where the exited one is listed first.

## B. What the security review requires

**B1. Every deploy leaves the stack's secrets on the host forever.** `claimBundledPackage` renames the sealed package into `<versions>/bundled.packages/claims/<uuid>/payload` and nothing ever removes it, and `pruneAll` deliberately never looks into `bundled.packages`. After N deploys the host holds N copies of `.env`, `deploy/config.json` and `engines/*/.env`, including rotated secrets. Close it inside the upgrade, under the guard, after a successful publication:
- Add `PostgresBundledShipmentRepository.supersedeStalePending(versionId)`: under the version row lock, every shipment of that version in state `registered` or `prepared` whose `expected_publication_revision` is below the row's current `publication_revision` becomes `superseded`. Return the records it changed. A database test in `manager/test/database/` (gated by `T04B_TEST_PG_PORT` like its neighbours) proves it supersedes exactly those, leaves the current publication and any pending shipment at the current revision alone, and that the identity trigger accepts the change.
- Add a package sweep, a small module in `manager/src/domain/versions/` with a name that says what it does, taking the versions root and a way to look up shipments by id. For each `claims/<uuid>` directory: remove it when the journal has that shipment as `published` or `superseded`, keep it when `registered` or `prepared`, keep it and report it when the journal does not know the id. For each `sealed-<uuid>` directory without a `.tmp` suffix: the same rule. For each `bundled.materializations/<id>` directory: remove it when the journal has a superseded shipment with that materialization id and kind `new`, keep it otherwise. Removals go through `assertOwnedVersionParent` and refuse symlinks the way `versionRemovalGuard.ts` does. Answer what was removed and what was kept, names only, never contents. Unit tests over a temp tree with a fake lookup cover every branch, including the unknown id.
- `ComposeUpgradeOperations.publish` runs, after a `published` activation: `supersedeStalePending` for the bundled version, then the sweep, and prints one stderr line per removed directory with the `[cli]` prefix. Failure of the sweep does not undo the publication: report it and continue to `startProject`. Test with the fake database that the order is publish, supersede, sweep.
- `deploy/README.md`, the half-way section: name `bundled.packages/` beside the guard, say that `sealed-<uuid>` and `sealed-<uuid>.tmp` directories the journal does not know are leftovers of deploys that failed before publication and how to remove them by hand, and that the upgrade cleans the rest itself.

**B2. The toolchain string can carry a quote into the host shell.** It is interpolated single-quoted into the remote heredoc. Tighten `assertToolchain` in `manager/src/cli/bundledSeal.ts` to `/^[A-Za-z0-9 ._\/+-]+$/` with the length limit kept, and apply the same check to `--toolchain` in `manager/src/cli/managerUpgrade.ts` before the guard. Tests for both commands: a quote, a semicolon and a control character are refused by name.

**B3. Directory modes follow the laptop's umask.** Set `process.umask(0o022)` at the start of `runBundledSeal` so directories seal as 0755 and plain files as 0644, which is what the engine containers need to read the published build, while the captured inputs stay 0600 because they are written with an explicit mode. In `copyOwnedTree` (`bundledSeal.ts:71`), chmod after `writeFile` the way `bundledSourceCapture.ts:67` does, so executables in a built directory keep 0755 whatever the umask. Test: seal under `process.umask(0)` inside the test, restore it after, and assert the sealed root, a nested directory, a plain file, an executable and `.env` carry 0755, 0755, 0644, 0755 and 0600.

**B4. Compose error output reaches the deploy log.** `ComposeUpgradeOperations.ts:174` quotes Compose's stderr in the thrown message, and a Compose failure can print the resolved service configuration, which carries the database password inside `DATABASE_URL`. The message names the subcommand, the project and the exit code only, and ends with "Run the same docker compose command on the host to see its output." Same for a killed command: carry `killed` and `signal` through `CommandResult` from `commandRunner.ts` and say "was killed after N seconds" instead of "exited with -1". Tests: a failing `up -d --no-build --remove-orphans` rejects `startProject` with a message that names the subcommand and the code and does not contain the stderr text, and a killed command is reported as killed.

**B5. The started API is never checked against the image the upgrade recorded.** Two overlapping deploys can retag `manager-api` between one deploy's build and its `up`. In `verifyProject`, after health, read the running api container id with `docker compose ps -q api`, then `docker inspect --format {{.Image}} <id>`, and refuse when it differs from `request.manager.imageId`, which keeps the guard held. Test both outcomes with the fake runner.

**B6. The manifest read on the host follows symlinks and has no size cap.** `ComposeUpgradeOperations.ts:119` uses a plain `readFile`. Read it through `readOwnedFile` from `ownedTreePaths.ts`, and refuse before reading when `lstat` reports more than 64 MiB, with a sentence naming the path. Tests: a symlinked manifest is refused, an oversized one (make it with `fs.truncate` to the cap plus one byte, which costs no disk) is refused.

**B7. `--compose-file` is the one path flag with no rule.** Require it absolute, canonical (`resolve(path) === path`) and inside `--mutable-root`, refused with the usage otherwise. Test.

**B8. The health probe buffers a body it never reads.** Replace `await response.arrayBuffer()` with `await response.body?.cancel()`.

**B9. Migration log lines land on the stdout the deploy captures.** `Database.migrate` logs through `Logger.info`, which is `console.info`, which is stdout, inside the command whose stdout must be exactly one JSON line. Give `Logger` one method that routes every level to stderr, with a JSDoc line saying why a command line needs it, and call it first thing in `manager/src/cli.ts` for every command. Test in `managerUpgradeCommand.test.ts`: with a fake database whose `migrate` logs through the Logger, stdout receives exactly one line and it parses.

**B10. The deploy script trusts the seal output and the identities it interpolates.** In `deploy/deploy.sh`, after the seal: read the JSON with one `node -e` that exits 1 naming the missing field when `commit` or `digest` is not a string, and check with bash regexes before the heredoc that `SHIPMENT_ID` is a uuid, `SHIPMENT_COMMIT` and `MANAGER_COMMIT` are 40 hex characters and `SHIPMENT_DIGEST` and `MANAGER_DIGEST` are 64. Test the checks exist in `managerDeployScript.test.ts`.

**B11. The repository's `.dockerignore` excludes only a root-level `.env`.** Its `.env` and `.env.*` lines do not match `manager/.env`, which holds `POSTGRES_PASSWORD` and is copied into the image build stage by `COPY manager ./manager`, and its bare `swarm-hls-stream` line does not match `manager/swarm-hls-stream`, which the Dockerfile says is never baked into the image. Change them to `**/.env`, `**/.env.*` and `manager/swarm-hls-stream`, and drop the two negation lines that re-include the stack's env files, which nothing in the image needs. This is one commit on its own with that reasoning in the body. If you can, verify with a local `docker build --target build -t t04b-context-check .` followed by `docker run --rm t04b-context-check sh -c 'test ! -e manager/.env && test ! -e manager/swarm-hls-stream/package.json && echo context-clean'`, then `docker rmi t04b-context-check`. If the build needs the network and it is refused or too slow, say so in the report and leave the change in.

## C. Cross-platform correctness of the package format

**C1. Symlink modes differ between macOS and Linux.** `ownedTreeInventory.ts` records a mode for symlink entries, and `sealBundledPackage` and `copyBundledArtifact` call `lchmod`, which exists only on macOS and is undefined on Linux, where a symlink is always 0777. A package sealed on the laptop with any symlink in it would either fail verification on the host or crash the copy. Record symlink entries with mode 0777 on every platform, never call `lchmod`, and keep the digest rule otherwise unchanged. Tests in the package and artifact test files: a symlink in a fixture inventories as 0777 whatever the platform reports, and a sealed package containing a symlink verifies. Check `manager/test/support/bundledArtifactFixture.ts` still seals (it has an `entry` symlink).
