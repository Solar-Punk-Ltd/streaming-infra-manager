## What is true today (anchors on feat/ai-remediation after the bundled-on-host merge)

A version's host-owned settings are three kinds of file under its config root `<versions>/<name>` (`configRootFor`, manager/src/domain/versions/stackPaths.ts): the base `.env`, `deploy/config.json`, and `engines/<engine>/.env`. They exist from the first successful build: `seedHostConfig` (StackVersionService.ts) seeds `.env` from `.env.sample` and `deploy/config.json` from `deploy/config.sample.json` when the root has none, the bundled version first carries the legacy tree's files over (`legacyHostConfig.ts`), and `completeHostConfigFromSamples` (`hostConfigCompletion.ts`) appends the sample's lines for keys the files lack. Every change is one revision: `.config-revision.json` with a generation and a sha256 per file, written under the directory lock `.config.lock` (`holdHostConfigLock`, `withHostConfigLock`, `commitHostConfig` in `hostConfigCapture.ts`). A build captures the revision current at publish (`captureHostConfig` in `publishStaging`) and writes those files into the build directory, and a deploy copies the build's base `.env` into the deployment's `.env.<name>` (`writeProfileEnv`, manager/src/utils/envUtils.ts:207) with the per-deployment keys upserted. A build of the same commit with a newer input generation gets a new build id `<commit>-r<n>` (`freeBuildId`). The only editor today is `manager/scripts/stack-config-edit.sh` over ssh: `<root> set <file> <source>...`, `<root> commit`, `<root> --unlock`. No API route reads or writes these files (manager/src/api/server.ts mounts). `GET /versions` answers `StackVersion` (common/src/stackVersions.ts:113-140) without settings. The Versions page lives in frontend/src/versions (VersionsPage.tsx, VersionCard.tsx, AddVersionForm.tsx, BuildLogPane.tsx, versionsApi.ts, versionText.ts), and the frontend has a browser test setup in frontend/test (versions-layout.test.mjs, headless Chrome, run separately from `pnpm test`).

The samples carry the documentation: comment lines above each key in `.env.sample` and `engines/<engine>/.env.sample` say what the key is. The secret-like keys of the stack today: base `STREAM_KEY` (the uploader's signing key, the manager writes it per deployment), `API_AUTH_TOKEN` (generated per deployment, a required secret of the contract), `PUBLISH_KEY_SECRET` (operator set, optional, at least 32 characters), engine `SRT_PASSPHRASE` (the manager writes it per deployment), `SRS_WEBHOOK_TOKEN` (generated per deployment, required), `OME_ADMISSION_SECRET`. Required secrets come from the version's contract (`requiredSecrets` in `stackContract.ts`), and the manager generates them in `profiles.stack_secrets` at the first deploy of a deployment.

## The design

1. **Read.** `GET /versions/:id/settings` answers the version's settings from its config root and the current build's samples: `{ generation, buildId, files: [...] }`. An env file is `{ path, kind: 'env', entries: [{ key, value, sampleValue, description, secret, generated }] }` in the order of the sample with the file's extra keys after it, where `description` is the sample's comment block above the key (comments only, the `#` stripped, joined with spaces), `secret` follows a shared name rule in `common` (the six keys above, plus any key ending in `_TOKEN`, `_SECRET`, `_PASSPHRASE`, `_PASSWORD` or `_KEY`), and `generated` is true for a key the manager fills per deployment (the contract's required secrets, `SRT_PASSPHRASE`, `STREAM_KEY`). `deploy/config.json` is `{ path, kind: 'json', text }`. A version with no config root yet (never built) answers 409 `settings_not_ready` with a message that settings appear after the first build. The route sits behind the session gate like the other version routes. Values are returned as they are, secrets included, because D13 makes them revealable and the session is the only reader. The UI masks them until revealed.

2. **Write.** `PUT /versions/:id/settings` takes `{ expectedGeneration, files: [{ path, entries: [{ key, value }] } | { path, text }] }`. Under one acquisition of the config lock (`withHostConfigLock`): refuse 409 `settings_changed` when the current generation is not `expectedGeneration`, refuse 400 on a key that is not a valid env name, on a value with a newline, on JSON that does not parse, or on a path outside the set. An env file is rewritten from its current bytes: an entry whose key exists replaces that line's value in place (the line's `export` prefix and spacing kept, comments and blank lines untouched byte for byte), a new key is appended, and an entry whose key is a known one but comes with `remove: true` deletes the line. One commit for all files, one new generation. The response is the new generation. Nothing else is written.

3. **Apply.** A saved revision reaches new deployments only through a build that captured it, and a full fetch and `pnpm` build is too heavy for a settings change. `POST /versions/:id/settings/apply` makes a new build of the current build's commit with the current revision: a new build directory whose tree is the current build's tree with the settings files replaced by the revision's, the same manifest fields with the new input generation, a new build id from `freeBuildId`, `.complete`, then `versions.publish`, then `pruneBuilds`. Files of the immutable tree are hard linked where the filesystem allows and copied otherwise (say which in the manifest), because a build is never modified in place so sharing bytes is safe, and the settings files are always fresh copies. The operation runs under the build mutex, refuses while a build runs (409 `build_busy`), and returns the new build id. Deployments made after it run on it. Running deployments keep their settings until they are redeployed, and the page says so. A version whose current build's commit no longer matches the pinned commit (bundled only) is applied all the same, the pin is the rebuild's business.

4. **The generated secrets rule.** When the version's base or engine env holds a non-empty value for a key the manager generates per deployment, new deployments get that value and the manager does not generate one. When it is empty, the manager generates as today. This touches where `stack_secrets` are created (ProfileService and `stackSecrets`) and where `SRT_PASSPHRASE` and `STREAM_KEY` are written (`writeProfileEnv`): the version's value is the default the per-deployment value falls back to, and an explicit per-deployment value still wins. Tests for both branches, for the base and the engine files.

5. **The page.** A `Settings` button on every version card (bundled included) opens `/versions/:id/settings`: one section per file in the order base env, deploy config, engines. Each env entry shows the key, the description under it, the value in an input, a `default` mark when the value equals the sample's, and for a secret a masked input with a `Reveal` toggle. A generated key shows the note "set per deployment by the manager unless you set a value here". `deploy/config.json` is a text area with JSON validation on save and a `Reset to sample` action. The footer has `Save`, `Save and apply` (save, then apply, with the apply outcome shown) and `Discard`. A 409 `settings_changed` shows "Somebody changed these settings since you loaded them" with a reload action, a 409 `build_busy` shows what is building. A version that is not ready shows the reason and no inputs. Mobile widths keep the layout usable (T18's rules). Shared types for the settings shapes live in `common`.

6. **Docs.** manager/README.md gets a paragraph on the settings page and the apply step under the versions section, deploy/README.md points at the page instead of `stack-config-edit.sh` for editing (the script stays for ssh use), and the handover gets a dated section.

## What must keep holding

- The lock: nothing reads and then writes a settings file outside one acquisition. `stack-config-edit.sh` keeps working alongside the API (its 30 second wait covers a page save).
- Builds stay immutable: apply never touches an existing build directory, only makes a new one.
- The bundled version takes the same routes as every other version. Update on it still rebuilds the pin.
- Key names only in logs, never values. The frontend never logs a value.
- The `secret` name rule is one function in `common`, used by api and frontend.

## Tests to write first

1. Route tests (versionsTestApp): GET shape for env and json files, descriptions from sample comments, `secret` and `generated` flags, 409 for a version with no config root, session gate.
2. PUT: in-place value replacement keeps every other byte, append of a new key, removal, 409 on a stale generation, 400 on a bad key, a newline in a value, bad JSON, a path outside the set. Mutation check: a save that rewrites comments must fail a test.
3. Apply: new build directory with the revision's files and the old tree, hard links or copies verified by inode where linked, new build id `<commit>-r<n>`, publish and prune, 409 while building, the old build kept as previous.
4. The generated secrets rule: version value used when set, generated when empty, explicit per-deployment value wins, for `API_AUTH_TOKEN`, `SRS_WEBHOOK_TOKEN`, `SRT_PASSPHRASE`, `STREAM_KEY`.
5. Common: the secret name rule.
6. Frontend: the page renders entries, masks secrets, reveals on toggle, marks defaults, disables when not ready, shows the 409 messages. A browser test in frontend/test for the page at a narrow width.
7. Database: the settings routes against Postgres for the generation check under concurrent saves (two PUTs, one wins, the other gets 409).
