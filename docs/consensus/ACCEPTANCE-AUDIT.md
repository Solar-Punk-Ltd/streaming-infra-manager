The follow-up design review accepts Bash/coreutils as the proposed existing connector. Debian Bookworm's [Bash package](https://packages.debian.org/bookworm/bash) and [coreutils package](https://packages.debian.org/bookworm/coreutils) establish the expected base capabilities. The [Bash manual](https://manpages.debian.org/bookworm/bash/bash.1.en.html) documents TCP redirection and waiting for either child. Invoke a fixed argument array through `env -i` and `timeout`, then Bash with startup files disabled and a constant program. Only the validated numeric port is substituted as a positional argument. Open one numeric-loopback TCP descriptor, preserve stdin before starting two byte-copy children, and stop/reap the remaining child when either copier ends. A separate timeout process group with TERM/KILL bounds orphan lifetime. Derive its lifetime from the validated preparation and POST budgets plus a bounded cleanup margin. A hard-coded 225 seconds would not cover every allowed 60-second session-preparation setting.

Local acquisition uses one configured Unix Docker socket connection. Remote acquisition uses a private OpenSSH master and private Unix forwarding, with connection fallback disabled on follow-up channels. The same Docker connection reads daemon identity, inspects the full container ID, creates its exec and starts the hijacked stream. With `Tty:false`, Docker stdin is raw but stdout/stderr use framing. The new decoder must handle split eight-byte headers and payloads, preserve binary stdout with backpressure, and refuse stderr, malformed/oversized frames or truncated termination. The existing `dockerStream.ts` log decoder merges streams and decodes text, so it cannot be reused. Never log raw inspect data, environment values, bridge stderr or HTTP bodies. The [Docker protocol reference](https://github.com/docker-archive/engine/blob/master/docs/api/v1.19.md) describes this framing.
