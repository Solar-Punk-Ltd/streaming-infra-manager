## The design

1. The manager pins a stack commit. `deploy/deploy.sh` writes `manager/.stack-commit` from the manager's own tree, `git rev-parse HEAD:manager/swarm-hls-stream`, which is the commit the submodule pin records, whether or not the submodule is checked out on the laptop. That file is the only thing about the stack the deploy carries, and it comes from the repository, not from anybody's checkout state.

2. The bundled version becomes an ordinary version whose ref is that commit. At boot, after the migrations and the legacy metadata refresh, the api reads the pin. If the bundled row has no complete build of that commit (no build, or a build of another commit), it starts a build of that commit through the same path an update takes (`startBuild` with `gitRef` = the commit), under the same build mutex, with the same SSE log, and sets the row's `git_ref` to the commit. If the build of that commit exists and is complete, nothing runs. If `.stack-commit` is absent (a developer laptop), the row stays legacy on `SHLS_ROOT`, as today. A boot never starts a second build while one is running (the mutex refuses, the boot logs and moves on). A boot after a failed build tries once more, which is what makes a transient network failure heal at the next restart.

3. `update` for the bundled version is allowed and means "rebuild the pinned commit". It refuses with a clear message when there is no pin. `add` with the name bundled still refuses. Removal still refuses. The UI enables Update on the bundled card with wording that says what it does ("Rebuild the version the manager ships with, commit <short sha>"), and the card shows the commit.

4. The build script accepts a 40-hex commit as `<ref>`. Existing clone: `git fetch --prune origin <sha>` then `checkout --detach --force FETCH_HEAD`, `reset --hard FETCH_HEAD`. No clone yet: `git init`, `git remote add origin <url>`, `git fetch --depth 1 origin <sha>`, `checkout --detach FETCH_HEAD` (a later fetch of a branch into the same clone must still work: use a full fetch if `--depth` makes that awkward, and say so in a comment). Branch and tag refs keep today's path. `.stack-commit` in the staging tree keeps being the checked-out commit.

5. Settings carry over and complete themselves.
   a. Before seeding, when the bundled config root `<versions>/bundled` holds no settings files and the legacy tree at `BUNDLED_STACK_ROOT` holds any of the set (`.env`, `deploy/config.json`, `engines/<engine>/.env`), those files are committed into the config root as generation 1 (through `commitHostConfig`), byte for byte, and a log line names them. The legacy tree is not modified. Only the bundled version does this, and only once, because after it the config root is not empty.
   b. Seeding from the samples stays for files the root does not have.
   c. Completion: a base `.env` that lacks keys the build's `.env.sample` declares is completed, not refused: the sample's own lines for the missing keys (the key with the sample's value, blank when the sample is blank) are appended, and the result is committed as a new revision under the config lock, with a log line naming the keys added. The build then captures that revision. The same rule holds for `engines/<engine>/.env` against `engines/<engine>/.env.sample` when both exist. A file that does not parse (the JSON) or cannot be read is still refused with today's messages. This applies to every version, since the bundled one now takes the same path.
   d. The revision written stays readable by the future settings page: keep `.config-revision.json` and the lock as they are.

6. The upgrade command loses the shipment. `ManagerUpgrade` phases become checking, stopping, migrating (the existing `installing` and `publishing` phases go), starting, verifying, then one more, `bundled`: after the api is verified, the command waits for the bundled row to reach a build of the pinned commit or a failure, by reading the `stack_versions` row (it has the database), polling every few seconds up to a bound given as `--bundled-timeout <seconds>` (default 1200). It prints the outcome. A failed or timed-out bundled build is printed with the row's last error and exits non-zero, but only after the guard is released, because the manager is running and the deployer can retry from the Versions page. The request no longer carries a shipment id, commit, digest or toolchain. `readPublication` keeps the first-use rule and the schema state (fresh, pre-journal, current) but no pending shipment. The deploy script's remote block passes `--bundled-timeout` and no shipment flags. Keep `< /dev/null`.

7. Migration 030 drops `bundled_shipments` and its triggers, and keeps `publication_revision` and its trigger (they came with 024 but are used elsewhere). Nothing has run 024 outside disposable databases, but the rule is still a new migration, never an edited one.

8. Everything listed under "the laptop path this brief removes" is deleted, with its tests. Do not leave dead exports. `stackPaths.ts` loses the package, claim, sealed and materialization helpers. `manager/src/cli.ts` loses `bundled:seal`. `deploy/deploy.sh` loses the stack build, the seal, the identity checks and the package rsync. Keep `manager/.stack-commit` generation (changed as in point 1) and everything else.

9. Docs. `deploy/README.md`: rewrite "What a deploy does to the bundled stack" and the section on what a stopped deploy leaves behind, and fix the stale paragraph at :240-262 that says the bee bind settings live on the laptop: they live on the server, in `<versions>/bundled/.env`, edited with `manager/scripts/stack-config-edit.sh` until the settings page exists, and a deploy never touches them. `manager/README.md`: the bundled paragraph (:267-271) says the bundled version is fetched and built on the host from the commit the manager pins, and `.stack-commit` is that pin. `docs/handover/main-v2-remediation.md`: one dated section at the end, "The bundled stack is built on the host", with what changed and the evidence.

## What must keep holding

- The first-migration and restart-consistency guarantee of T04b: a deployment created while the bundled row was legacy keeps reading the legacy tree until an explicit rollout moves it. Its tests (`bundledPublication.test.ts`, `bundledBootRecovery.test.ts`, and whatever else asserts it) are adapted to the new boot behaviour, not deleted. If you find the guarantee is not actually tested today, say so in the handover section instead of inventing a claim.
- The build mutex: one build at a time per manager, the boot-triggered build included.
- `verifyBundledArtifact` semantics for builds (manifest, complete marker, digest) stay for the bundled builds the new path produces, through the same `publishStaging`.
- The api boots even when the bundled build fails or GitHub is unreachable. A failed bundled build is a failed version row, visible on the Versions page, never a refusal to start.
- Nothing in the unit suite talks to the network or to Docker. The build script's new commit path is covered by the script-text test (`stackVersionBuildScript.test.ts`) and by a test that runs the script's fetch part against a local bare repository if you can do that without the https-only url check getting in the way (an env override for tests is acceptable if it cannot be set on the host by accident, and say what you chose).
