# T09 completion slice: what the reviews found and what changes

Written by Fable on 2026-09-10 after the Opus implementation (branch `feat/t09-receipt-polling`, head 74e375e, 18 commits over 3e3465a) and two parallel reviews on detached worktrees at that head.

## F. Fable's own findings

- **F1 (MEDIUM, the dialog flashes during every automatic re-read).** `TransferController.current()` clears `detail` at the start of every `restore()`, so while the dialog re-reads the record every 10 seconds the evidence panel is replaced for a moment by "The manager has not returned a verified record for this request. Its transaction outcome is unknown." That sentence is untrue at that moment, and it now happens every 10 seconds unattended. Fix: a restore started by the polling cadence keeps the shown `detail` until the lookup answers, and then applies the same outcome rules as before, including clearing it on `lookup_missing` and `incomplete_response`. The manual Refresh keeps its current behaviour or adopts the same, the implementer decides and tests both. The existing dialog tests that pin the identity-conflict and busy paths stay green.
- **F2 (MEDIUM, the poller is silent in production).** `createChequebookOperationsService` builds the poller with `dependencies.receiptPolling`, which `index.ts` never passes, so `log` is the no-op default and neither "Receipt polling could not read the transfer journal" nor the per-tick notes reach the manager's logger. Fix: default the poller's log to the manager's `Logger` (info for the notes, warn for the journal read failure) in the factory, keep the option for tests, and add a factory test that the production default is not the no-op.

## Decisions the implementer took, ruled on

2. The mock journal does not settle on its own, `mock-manager.mjs` keeps doing it: accepted, the reason (three suites settle by hand at exact points) is sound.

4. The composition extracted into `manager/test/support/connectedChequebook.ts`: accepted.

## C. Correctness review findings (Opus, worktree at 74e375e, disposable Postgres, sixteen mutations run)

Verdict: everything the brief asked for is present and the state machine is right. Two findings are wrong information shown to an operator on a money screen, both confirmed in a real browser.

- **C1 (HIGH, a conflicted transfer is shown as polled and told to press a button it does not have).** `frontend/src/transfers/receiptPolling.ts` decides the sentence and the re-read cadence from `state` and `receiptPollUntil` only. The manager's rule has a third condition: `listAwaitingReceipt` and `ChequebookReceiptCheck.check` both exclude `failure_reason = 'hash_conflict'`. A row that is `submitted` with a conflict keeps its deadline (the SQL suite pins that shape at `chequebookOperations.test.ts:775-777`), so the page says the manager checks it every 20 seconds (it never does), re-reads it every 10 seconds for 30 minutes, and after the deadline says "Use Check" while `canCheckTransfer` returns false for a conflict, so there is no Check button. Fix: `PolledTransfer` includes `failureReason`, `receiptPollDeadline` returns null on `hash_conflict`, the eight fixture literals in `receiptPolling.test.ts` gain `failureReason: null`, one unit case and one browser case for a conflicted row, and `docs/features/chequebook.md:105` names the conflict beside `submitting` and `unknown`.
- **C2 (HIGH, the dialog flashes "Its transaction outcome is unknown" on every automatic re-read).** The same as F1, confirmed: `TransferController.current()` builds its snapshot from `empty()` which sets `detail: null`, so every 10 second tick replaces the evidence panel with the unknown-outcome paragraph and the spinner, measured at 317 to 337 ms per re-read with 300 ms manager latency, and `polledUntil` going null tears the interval down and rebuilds it, so the real cadence is 10 seconds plus a round trip. Fix: in `current()`, retain `detail` (beside the existing `blocking` and `blockingReason` retention) when the loaded intent is the request already shown, and make the `lookup_missing` and `incomplete_response` branches clear it explicitly so no stale record survives a real answer. A case in `transfer-polling-browser.test.mjs` samples the dialog text across a re-read and requires the unknown-outcome sentence never to appear while the record is `submitted`. The dialog and adapter browser suites stay green.
- **C3 (MEDIUM, one failed re-read ends the automatic re-reads for good).** `useTransferRead` schedules nothing from its rejection branch, and a failed restore leaves the dialog's `state.detail` null so `polledUntil` stays null. Measured: one synthetic 503 and the page never read again. A 15 second read timeout, a tunnel blip or a manager restart during a deploy is enough. Fix: `useTransferRead` remembers the last value that warranted repeating and schedules the next attempt from the failure branch too while that value still warrants one, so a blip costs one cycle. The dialog derives `polledUntil` from the last successful detail, which the C2 fix gives it. A browser case with one failed read in the middle of polling.
- **C4 (MEDIUM, `stop()` can hold the manager's shutdown for about five minutes).** The `for` loop over the due rows never looks at `stopped`. Measured 1985 ms with 20 rows at 100 ms each. In production, 20 rows at the inspector's 15 second timeout during an RPC outage is about 298 seconds, past systemd's default 90 second stop timeout, so the manager would be killed mid-shutdown with the transport cleanup unverified. Fix: `if (this.stopped) break;` at the top of the loop, and a case with two slow rows where a `stop()` issued during the first never checks the second.
- **C5 (MEDIUM, every poll bumps the revision, which makes the operator's Check refuse).** `recordReceipt` writes a row and bumps `revision` on every poll including an unchanged `pending`, measured at one bump per poll, about 90 writes over a budget. `useTransferRecovery.fresh()` refuses when the revision moved, and `TransferRecoveryActions` is keyed on the revision so it remounts and aborts an in-flight action. With re-reads every 10 seconds and polls every 20, a good share of Check presses during polling come back "The saved transfer changed", and the notice only shows while loading. Ruling (Fable): fix it at the source. When the normalized observation equals the stored one, `recordReceipt` refreshes `receipt_checked_at` only and leaves `revision` and `updated_at` alone, still under the same `WHERE` clause. A changed observation, including a `could_not_check` whose history cursor moved, writes as today. The in-memory fake mirrors it. The interface comment on `recordReceipt` says "a check that changes the observation advances the revision, an unchanged one only records when it was made". SQL cases: an unchanged `pending` twice leaves the revision alone and moves `receipt_checked_at`, a changed observation bumps, and a manual Check that lands between two polls succeeds. Fable notes the existing concurrency test "accepts only one observation from concurrent checks at the same revision" must stay green: two writers with different observations still race on the revision, two writers with the same unchanged observation both succeed as no-ops.
- **C6 (MEDIUM, the poller's log goes nowhere in production).** The same as F2 and S2.
- **C7 (MEDIUM, nothing pins the no-renewal guard).** The same as S4, with the sequence the reviewer found reachable: recovery adopts a candidate hash and moves the row to `submitted` with a budget, then the late `recordSubmission` arrives with that same hash, is owned, and reaches the `CASE`. One assertion after `submittedOperation()` in the "opens one receipt polling budget" test, or the S4 test, turns the mutation red.
- **C8 (withdrawn).** The reviewer reported that the dev mock never settles a submitted transfer. Fable checked: `frontend/dev/mock-manager.mjs` line 226 schedules `observeReceipt(..., settled)` after a submission, so `pnpm dev:mock` does show the flow, as the implementer said. Fix: none, except that `docs/testing/t09-browser-intents.md` says where the mock's automatic settlement lives so the next reader does not look for it in the journal.
- **C9 (LOW).** The same as S6.
- **C10 (LOW).** The same as S1.
- **C11 (LOW, `useTransferRead`'s repeat argument must be referentially stable and nothing says so).** One line on the `RepeatedRead` interface. `TransferDetailPage` already memoizes it.

## S. Security review findings (Opus, worktree at 74e375e, disposable Postgres, nine mutations run)

Verdict: nothing leaks, nothing can be driven into submitting, recovering or scanning. The findings are one runaway in the test fixtures and places where the code is right today and no test would notice if it stopped being right.

- **S1 (HIGH, every browser fixture leaves a 9 MB Vite cache behind).** `frontend/test/support/transfer-fixture.mjs` gives every fixture a fresh `T09_VITE_CACHE` under a `t09-http-*` evidence directory in the temp directory and never removes it. Measured on this machine: 414 such directories, 3.6 GB, each holding a 9.2 MB `vite-cache` and an empty `vite.log`. The pattern predates the slice, the slice triples the rate (the intent, polling and connected suites add nine fixtures per full run). Fix: one shared cache for all fixtures, `join(<frontend root>, 'node_modules', '.vite-t09')`, which also makes cold starts faster, and `stop()` removes an evidence directory that holds nothing but an empty log. Fable adds: the 414 directories on this laptop get removed once the fix is in, after a content check that each holds only `vite-cache` and `vite.log`, and the count and bytes go into the report to Levi.
- **S2 (MEDIUM, the poller is silent in production).** The same as F2. `index.ts` passes no `receiptPolling`, so a journal that stops answering is never logged and every submitted transfer silently stops reaching a verdict. Fix as F2, with `logger.warn` for the failure line and `logger.info` for the notes.
- **S3 (MEDIUM, the connected fixture server could bind every interface and nothing would notice).** `manager/test/support/connectedChequebookServer.ts:76` binds `127.0.0.1` today. Mutation S2 (`0.0.0.0`) left the connected browser suite green. What would then be on the network is the real money router behind the real session gate with a published fixture password. Fix: after `listen`, assert `server.address().address === '127.0.0.1'` and exit non-zero otherwise, and the same assertion in `connectedChequebook.ts` where the Unix socket directory is created (loopback and a `0700` directory).
- **S4 (MEDIUM, the no-renewal rule is not pinned by a test).** Mutation S7 replaced the `COALESCE` in `openPollBudget` with a plain assignment and all 58 SQL tests stayed green. The reviewer proved the path is load-bearing: `recordSubmission` with the same hash on a row already `submitted` takes the owned branch and reaches `openPollBudget`. Fix: the reviewer's test in `chequebookOperations.test.ts`, "keeps the first budget when the same hash is recorded again" (wait 1100 ms, record the same submitted outcome again, assert the deadline is unchanged), red under the mutation, green on the branch.
- **S5 (MEDIUM, the dialog's stop-at-deadline is untested).** Mutation S9 dropped the `isPollingReceipt` gate in `useTransferController` and the frontend unit run and the polling browser suite stayed green, because the polling suite's dialog case only ever has a live budget. The code does stop, the reviewer traced it. Fix: a fourth case in `transfer-polling-browser.test.mjs`, the dialog on an operation whose deadline is past, asserting the GET count does not move across one `RECEIPT_READ_INTERVAL_MS + 3000` wait, the shape of the existing detail-page case.
- **S6 (MEDIUM, the connected fixture's setup and teardown are not fail-safe).** `connectedChequebook.ts:118-185`: `startConnectedChequebook` creates the schema, runs migrations, seeds, makes the temp directory and listens, with no unwinding on a partial failure, and two live pools then hold the event loop open. `close()` is a straight line from `service.shutdown()`, which can reject through `closeTransports()`, skipping the socket, directory, pool and `DROP SCHEMA` steps. Fix: try/unwind/rethrow in the start, and in `close()` run every step and rethrow the first error at the end.
- **S7 (LOW, the Vite fixture could take a port from the environment unnoticed).** Mutation S5 made `transfer-vite.mjs` read `T09_VITE_PORT` and the intent suite ran happily on 54291. `strictPort` keeps a collision loud, which is why this is low. Fix: a small Node test on `transfer-vite.mjs` or the fixture that asserts the port came from the probe (the child reports the port it bound, assert it differs from a value planted in the environment), or a review note in the file header.
- **S8 (LOW, `isTimestampOrNull` accepts more than an ISO timestamp and no ceiling).** `frontend/src/transfers/transferEvidence.ts:7-8` accepts anything `Date.parse` reads, such as `'2026'`, and any distance into the future. Fix: the ISO shape, and clamp `receiptPollDeadline` to `now + RECEIPT_POLL_BUDGET_MS` so a dishonest field cannot keep a tab re-reading for longer than the manager could be polling.
- **S9 (LOW, under an RPC outage a tick can take five minutes while the page promises 20 seconds).** Twenty rows times the inspector's 15 second timeout. Bounded and graceful. Fix: the sentence says "about every 20 seconds, longer while the chain endpoint does not answer", and `docs/features/chequebook.md` records the worst case.
- **S10 (LOW, the poller's narrowing is type-level only).** It receives the whole repository and the whole receipt check at runtime. Fix, cheap and worth it: the factory passes bound object literals exposing `listAwaitingReceipt` and `check` only.

Mutation table: S1 RED, S2 GREEN (finding S3), S3 RED, S4 RED, S5 GREEN (finding S7), S6 RED, S7 GREEN (finding S4), S8 RED, S9 GREEN (finding S5). Confirmed correct: the two log lines carry a validated UUID and a closed enum only, the call graph reaches `listAwaitingReceipt` and `check` and nothing else, `receipt_poll_until` is written by two UPDATEs through `openPollBudget` only, no client value reaches a cadence or a bound, no change under `manager/src/api/`, the fixtures bind loopback on port 0 with IPC as the only control channel, the socket directory is 0700, Chrome runs without `--no-sandbox`, cleanup left zero schemas, directories, profiles or processes after a full run, an injected failure and a SIGKILL of the fixture's parent.
