## What this closes

The manager's own deploy (`deploy/deploy.sh`) used to rsync the bundled streaming stack over the tree the engines mount, and a later version had the API publish an `bundled.incoming/` tree at boot. Both are gone from the merged code: `StackVersionService.syncBundled` now only refreshes the metadata of a still-legacy bundled row (commit `15c9565`, tests `manager/test/unit/bundledBootRecovery.test.ts` and `manager/test/database/legacyMetadataRefresh.test.ts`). The durable replacement is written and tested up to the command object, but nothing calls it and `deploy.sh` still ships to `bundled.incoming`. So today a manager deploy leaves the shipped stack on the host and never publishes it. The 12 red tests in `manager/test/unit/bundledPublication.test.ts` are the old boot-publication tests.

This slice wires the existing pieces into a working deploy: a laptop-side command that seals the shipment, a host-side command that runs the upgrade under the durable guard and publishes, the deploy script that calls both, and the tests that replace the 12 red ones.

## What already exists, read these first

All under `manager/src/domain/versions/` unless noted.

- `bundledSourceCapture.ts`: `exportPinnedBundledSource(source, destination, run?)` exports the git objects of the checkout's HEAD commit into a fresh private tree (submodules included, dirty application files refused, laptop-owned inputs allowed). `captureBundledInputs(source, destination)` copies the committed host-input revision of `source` (`.env`, `deploy/config.json`, `engines/*/.env`, see `hostInputPaths.ts`) into the exported tree and writes `.config-revision.json` there. A checkout without a committed revision refuses. `hostConfigCapture.adoptHostConfig(root)` writes generation one from the files present, which is the explicit adoption step.
- `bundledShipmentPackage.ts`: `sealBundledPackage(source, destination, {shipmentId, commit, inputs})` copies the tree into `destination`, records every path, type, mode and sha256 in `.shipment-manifest.json` (mode 0600) and returns the identity `{shipmentId, commit, digest}`. `verifyBundledPackage(root, identity)` checks a whole tree against it. The tree must not contain symlinks that point outside it. Node modules must not be in it.
- `bundledPackageClaim.ts`: `claimBundledPackage(readyPath, claimDirectory, identity)` renames the ready package into `<claim>/payload` and verifies it.
- `BundledPublicationCommand.ts`: `new BundledPublicationCommand(shipments, claimsRoot, packagesRoot = dirname(claimsRoot))` and `publish({identity, readyPath, toolchain, reuseFromShipmentId?})`. `readyPath` must equal `join(packagesRoot, 'sealed-<shipmentId>')`. It registers the shipment in `bundled_shipments` (migration 024), claims the package, reserves the build id `<commit>-r<uuid as decimal>`, materializes into `<versions>/bundled.materializations/<id>` and renames into `<versions>/bundled.builds/<buildId>`, verifies, and activates: the `stack_versions` row named `bundled` moves to layout `builds` with that build id and the receipt is stored, in one transaction. A rerun with the same identity returns the stored receipt. Database tests: `manager/test/database/bundledPublicationCommand.test.ts`, gated by `T04B_TEST_PG_PORT`.
- `PostgresBundledShipmentRepository.ts`: takes `(pool, bundledRootPath)`. Use `configRootFor(versionsRoot, 'bundled')` from `stackPaths.ts` for the root path, which is `<versions>/bundled`.
- `ManagerUpgrade.ts`: `runManagerUpgrade({guardRoot, mutableRoot}, request, operations)`. The request is `{shipment: {shipmentId, commit, digest}, manager: {sourceCommit, sourceDigest, imageId}, project}` with strict formats (uuid v4, 40-hex commit, 64-hex digests, `sha256:<64 hex>` image id, compose project name). The operations interface is `readPublication, stopApi, installSources, publish, startProject, verifyProject`. The guard (`managerUpgradeGuard.ts`) is a directory outside the mutable install. Tests `manager/test/unit/managerUpgrade.test.ts` show the contract, including that an unfinished run keeps the guard and a rerun refuses with "Manager upgrade is already owned or in progress."
- `readManagerPublication.ts`: `readManagerPublication(pool, identity)` inspects the schema read-only under the migration lock and answers `fresh`, `pre-journal` or `journal` with the current revision. It never turns a database error into revision zero.
- `Database.ts` (`manager/src/domain/`): `migrate()` runs the SQL files under one advisory lock, `MIGRATION_LOCK_KEY`.
- `manager/src/cli.ts`: the existing command line, one command `user:add`. It imports `utils/config.ts` at module load, and that module throws without `DATABASE_URL`.
- `manager/Dockerfile`: the API image has node, `docker-cli`, `docker-cli-compose=5.1.4-r1`, `rsync`, `openssh-client`, git. `CMD node dist/index.js`. `manager/docker-compose.yml`: service `api` mounts `/var/run/docker.sock`, the repo at `/home/solarpunk/streaming-infra-manager`, the data root and the versions root at identical paths, and sets `DATABASE_URL`, `SHLS_ROOT`, `STACK_VERSIONS_ROOT`, `BEE_DATA_ROOT`, `PUBLIC_HOST`. On the host the compose project name is `manager` (the directory name), so the built image is `manager-api`.
- `deploy/deploy.sh`: builds the stack on the laptop with `pnpm -C manager/swarm-hls-stream -r build` (outputs `packages/client/dist`, 8 MB, and `packages/stream-uploader/dist`, 200 KB, both gitignored), writes `manager/.stack-commit`, rsyncs the repo without the stack tree, rsyncs the stack into `bundled.incoming.tmp` and renames it, then runs `docker compose up -d --build --remove-orphans` on the host with the edge profile logic. Its test is `manager/test/unit/managerDeployScript.test.ts`, which reads the script text.
- `manager/test/support/bundledArtifactFixture.ts` builds a sealed package for tests. `manager/test/support/stackFixtures.ts` has `V3_FIXTURE`, a real stack tree.

## The flow to build

Laptop, in `deploy.sh`:

1. Build the stack as today. Write `manager/.stack-commit` as today (the legacy row still reads it).
2. `SHIPMENT_ID=$(uuidgen | tr 'A-Z' 'a-z')`. One fresh id per deploy run. Replay of an old id is a later feature.
3. Build the manager's own code so the CLI exists locally: `pnpm --filter @streaming-infra-manager/api... build`. Then run `node manager/dist/cli.js bundled:seal --source manager/swarm-hls-stream --out "$SEAL_DIR" --shipment-id "$SHIPMENT_ID" --dist packages/client/dist --dist packages/stream-uploader/dist --adopt-inputs --toolchain "node $(node --version) pnpm $(pnpm --version) $(uname -s)/$(uname -m)"`, with `SEAL_DIR` a `mktemp -d` outside the repo, removed at the end of the script. The command prints one JSON line `{"shipmentId","commit","digest","path"}` on stdout and nothing else on stdout. Everything else goes to stderr. Read the three identity values from it.
4. Repo rsync as today, unchanged.
5. Ship the sealed package: `ssh host mkdir -p "$REMOTE_VERSIONS_ROOT/bundled.packages"`, `rsync -a --delete "$SEAL_DIR/sealed-$SHIPMENT_ID/" "host:$REMOTE_VERSIONS_ROOT/bundled.packages/sealed-$SHIPMENT_ID.tmp/"`, then `ssh host mv ...tmp ...sealed-$SHIPMENT_ID`. Use `-a` so modes and symlinks survive. Do not use `-z --delete` variations that drop `-p`. The `bundled.incoming` directory and everything about it go away.
6. Manager identity: `MANAGER_COMMIT=$(git rev-parse HEAD)`, `MANAGER_DIGEST=$(git ls-tree -r --full-tree HEAD | shasum -a 256 | cut -c1-64)`.
7. Remote block: `cd $REMOTE_PATH/manager`, export `PUBLIC_HOST`, `BEE_DATA_ROOT`, `STACK_VERSIONS_ROOT` as today, `docker compose build`, `IMAGE_ID=$(docker image inspect --format '{{.Id}}' manager-api)`, then
   `docker compose run --rm --no-deps -T api node dist/cli.js manager:upgrade --shipment-id ... --commit ... --digest ... --manager-commit ... --manager-digest ... --image-id "$IMAGE_ID" --project manager --compose-file /home/solarpunk/streaming-infra-manager/manager/docker-compose.yml --mutable-root /home/solarpunk/streaming-infra-manager --toolchain "..." [--public-edge]`.
   `--no-deps` is deliberate: the upgrade decides itself whether Postgres may be started or created. The one-off container joins the project network, so `postgres` and `api` resolve by name inside it. The edge profile decision (`MANAGER_DOMAIN` parsing) stays in the script, and only the flag crosses.
8. Print the receipt line the command returned, then the tunnel hint as today. Never run `docker compose config` without `--quiet` anywhere, in scripts or tests.

Host, inside `manager:upgrade` (runs from the new image):

- Build the `ManagerUpgradeRequest` from the flags and let `captureRequest` reject bad ones. `guardRoot = join(config.stackVersionsRoot, '.manager-upgrade')`, `mutableRoot` from the flag. Add `managerUpgradeGuardRootFor(versionsRoot)`, `bundledPackagesRootFor(versionsRoot)`, `bundledPackageClaimsRootFor(versionsRoot)` and `sealedBundledPackagePathFor(versionsRoot, shipmentId)` to `stackPaths.ts`, with the same doc style as the neighbours. Delete `BUNDLED_INCOMING_DIR` and `bundledIncomingRootFor` together with their last uses.
- Operations, a class `ComposeUpgradeOperations` in `manager/src/cli/` taking an injected `CommandRunner` (`run(argv, {cwd?, env?, timeoutMs}) -> {code, stdout, stderr}`, spawned with `execFile`, never a shell, killed on timeout, secrets never logged) and an injected `fetch`. Every docker call is `docker compose -p <project> -f <compose file> --project-directory <dir of the compose file> <subcommand...>` with a bounded timeout.
  - `readPublication`: decide about Postgres first. If the `postgres` service container is running and healthy, read. If a container exists but is not running, `up -d --no-build postgres` and wait for healthy, bounded. If no container exists: if the project volume `manager_manager-pg` is absent and no `api` container exists, this is first use, so `up -d --no-build postgres`, wait, and the schema read must answer `fresh`, anything else refuses. If the volume exists, `up -d --no-build postgres` and wait (this is an existing database, not revision zero). If the volume is absent but an `api` container exists, refuse and say what was found. Then `readManagerPublication(pool, identity)` on a pool from `config.databaseUrl`. Any read error propagates.
  - `stopApi`: `stop api`, then verify no running `api` service container remains. Only the API. Web, edge, Postgres and every deployment's containers keep running.
  - `installSources`: the manager sources were already rsynced and the image already built before the guard, and the running API takes its code from its image, so this step verifies rather than installs: the sealed package exists at `sealedBundledPackagePathFor` and its manifest parses to the request's identity (`parseBundledPackageManifest`, compare digest and commit). A mismatch refuses before anything is published. Write that reasoning into the class comment so a reader knows why nothing is copied here.
  - `publish`: `await database.migrate()` first (the old API is stopped by now, which is the rule: never migrate under a running old API), then `BundledPublicationCommand.publish({identity, readyPath, toolchain})` with `claimsRoot = bundledPackageClaimsRootFor(versionsRoot)`. `published` returns the receipt. `superseded` throws with a sentence saying a newer publication won. No reuse detection in this slice: every deploy is a new build, the shipment is 16 MB and `pruneAll` keeps only what is current, previous, referenced or pending.
  - `startProject`: with `--public-edge`: `--profile public up -d --no-build --remove-orphans`. Without it: `up -d --no-build --remove-orphans`, then `--profile public rm -sf edge`, then verify `--profile public ps -q edge` is empty, refusing otherwise with the same message the script prints today (the host is still answering on 80 and 443).
  - `verifyProject`: poll `http://api:9876/health` until it answers 200, bounded at 90 seconds, then check the edge state matches the flag. Failure throws, which keeps the guard held on purpose.
- Output: on `completed` or `already-completed`, one JSON line `{"state", "receipt": {"shipmentId","versionId","buildId","publicationRevision","publishedAt"}}` on stdout, exit 0. On any failure, `[cli] <one sentence>` on stderr, exit 1. When the guard refuses because a directory exists, also print the guard path and the `phase` from its `owner.json` (read only, through the guard's own reader, never by hand-parsing a symlink) and the sentence "A person checks the host before removing that directory." Never remove the guard automatically.
- `cli.ts` becomes a dispatcher: `user:add` moves to `manager/src/cli/userAdd.ts` with identical behaviour and usage text, `bundled:seal` to `manager/src/cli/bundledSeal.ts`, `manager:upgrade` to `manager/src/cli/managerUpgrade.ts`. The config module is imported only inside the commands that open the database, so `bundled:seal` runs on a laptop without `DATABASE_URL`.

Laptop, inside `bundled:seal`:

- Flags: `--source <checkout>`, `--out <dir outside the checkout>`, `--shipment-id <uuid>`, `--dist <relative dir>` repeatable, `--adopt-inputs`, `--toolchain <text>`. All required except `--adopt-inputs`.
- Steps: `exportPinnedBundledSource(source, join(out, 'export'))`. For each `--dist`, refuse when it is missing in the checkout, naming it and the build command, otherwise copy its regular files into the export at the same path (directories created as needed, symlinks refused, nothing outside the export written). If the checkout has no `.config-revision.json`: with `--adopt-inputs`, `adoptHostConfig(source)` and say on stderr which generation and files were adopted, without printing file contents, else refuse and name the flag. `captureBundledInputs(source, export)`. `sealBundledPackage(export, join(out, 'sealed-<id>'), {shipmentId, commit, inputs})`. Remove the `export` tree. Print the JSON line. The toolchain flag is only echoed in the JSON for the deploy to pass on, it is not part of the package.
